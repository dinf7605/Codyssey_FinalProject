# 실사용자 테스트 운영 가이드

> 기획서 8장(실사용자 테스트 계획)을 실제로 돌리기 위한 진행자용 문서.
> 참여자에게 보내는 글은 [참여자안내.md](참여자안내.md), 설문·인터뷰는 [설문_인터뷰.md](설문_인터뷰.md),
> 결과는 [리포트.md](리포트.md)에 채운다.

| 항목 | 내용 |
|---|---|
| 서비스 | https://codyssey-final-project.vercel.app |
| 인원 | **5명 이상** (목표 7명 — 중도 이탈 대비) |
| 대상 | 자격증·공모전을 **실제로 준비 중인** 대학생·취준생 (팀원·팀원 계정 제외) |
| 일정 | 모집·온보딩 10-05(월)~06(화) → **사용 10-06(화)~10(토), 5일** → 사후 인터뷰·설문 10-11(일)~12(월) → 4차 측정 10-13(화) |

> 원래 계획(10-08~12)보다 이틀 당겼다. 배포가 10-05 에 끝나 피드백 반영 시간을 더 확보하려는 것.
> 날짜를 바꾸면 이 표와 참여자 안내문, 지표 스크립트의 `--start/--end` 만 바꾸면 된다.

## 1. 시작 전 체크리스트 (진행자)

- [ ] **구글 로그인 범위** — OAuth 동의 화면이 '테스트' 상태면 참여자 Gmail 을 **테스트 사용자로 등록** (Google Cloud → Google 인증 플랫폼 → 대상). 앱을 게시했다면 생략. 이메일 가입은 등록 없이 누구나 된다
- [ ] **배포 상태** — `https://codysseyfinalproject-production.up.railway.app/contests?limit=1` 이 공고를 돌려주는지 (503 이면 Railway 환경변수)
- [ ] **자동 작업** — GitHub Actions 의 Contest jobs · Plan jobs 최근 실행이 초록, Railway 워커 로그에 오류 없음
- [ ] **AI 비용 한도** — 관리자 화면 'AI 비용' 확인. 참여자 7명이 계획을 여러 번 만들면 하루 수십 회 호출 — `AI_DAILY_BUDGET_USD`(기본 5달러) 80% 에서 비회원 AI 가 막힌다
- [ ] **참여자 명단** — 진행자만 보는 곳(팀 비공개 문서)에 `P번호 · 이름 · 이메일 · 준비 중인 목표 · 알림 그룹` 기록. **저장소에는 이메일을 올리지 않는다**
- [ ] **동의서 회수** — [참여자안내.md](참여자안내.md) 3절. 구글 폼 체크박스 또는 서면

### 알림 강도 그룹 (FR-ALARM-02 독촉 검증, 기획서 8-2 정성 3번)

참여자를 둘로 나눠 첫날 마이페이지 알림 설정을 맞춰 달라고 안내한다. 사후 설문 B 문항으로 비교한다.

| 그룹 | 설정 | 인원 |
|---|---|---|
| A | 알림 강도 **보통** (기본값) | 절반 |
| B | 알림 강도 **강** + '학습 독촉' 켜기 | 나머지 |

> 결론에 따라 기본값('약' / '보통')을 정한다 (기획서 11장 미결정 항목).

## 2. 기간 중 할 일

| 언제 | 할 일 | 담당 |
|---|---|---|
| 첫날 | 사전 인터뷰 10분 · 가입·온보딩을 옆에서(또는 화면 공유로) 지켜보며 **막힌 곳만 메모** — 도와주기 전에 30초 기다린다 | 진행자 |
| 매일 22시 | 단톡에 하루 한 줄 질문 (아래) · 버그 제보 받기 | 진행자 |
| 매일 아침 | 지표 스크립트로 전날 기록 확인 → 하루 종일 기록이 없는 참여자에게 개별 연락 (재촉 아님, 막힌 게 있는지) | 진행자 |
| 버그 즉시 | GitHub 이슈 등록 (`user-feedback` 라벨) · 서비스가 멈추는 버그만 기간 중에 고치고, 나머지는 기간 뒤 | 담당 파트 |

**매일 한 줄 질문 (예시)** — "오늘 일정 중 하나라도 해 보셨나요? 안 맞았던 점 한 가지만 알려 주세요."

> 기간 중 배포는 **멈추는 버그 수정만**. 화면이 바뀌면 참여자가 헷갈리고 전후 비교가 흐려진다.

## 3. 지표 뽑기

```bash
cd backend
# 참여자 이메일 파일(한 줄에 하나)은 저장소 밖에 둔다
python -m scripts.user_test_metrics --start 2026-10-06 --end 2026-10-10 --emails-file ../../participants.txt
```

- 결과는 P1, P2 … 로만 나온다 (이메일 짝은 `--show-emails` 로 화면에만)
- 계산 규칙은 `backend/services/user_test_metrics.py` 맨 위 표
- 매일 돌려 [리포트.md](리포트.md) 2절에 마지막 결과를 붙인다

| 지표 | 목표 | 출처 |
|---|---|---|
| 일정 준수율 | 60% 이상 | `plan_blocks.done` |
| 체크포인트 달성률 | 70% 이상 | 주마다 일요일까지 그 주 블록 완료 |
| 재조정으로 옮긴 블록 | 30% 이하 | `plan_changes` (nightly) |
| 목표 추천 적합 | 80% 이상 | `goal_feedback` (관심 있음/없음) |
| 공모전 추천 도움됨 | 90% 이상 | `contest_feedback` |

> 체크포인트는 일요일이 지나야 판단된다. 10-06~10 테스트라면 일요일(10-11) 밤을 넘긴 뒤 `--end 2026-10-11` 로 한 번 더 뽑는다.

## 4. 피드백 처리 (기획서 8-3)

1. 수집 — 단톡·설문·인터뷰·이슈
2. 분류 — 버그 / UX / AI 품질 / 신규 요구
3. 우선순위 — 영향(서비스를 못 쓰게 하는가) × 빈도(몇 명이 말했는가)
4. GitHub 이슈 (`user-feedback` 라벨) — 제목에 P번호, 본문에 재현 순서·화면
5. 5주차(10-12~) 반영 → 10-13 4차 측정으로 효과 확인
6. **반영하지 않은 것도 이유와 함께** [리포트.md](리포트.md) 4절에 남긴다
