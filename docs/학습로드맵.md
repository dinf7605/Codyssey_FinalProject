## 1. 팀 경험을 반영한 스택 조정 4가지

기획서 초안은 일반적인 기준으로 골랐다. 팀이 Make·Python·Vercel을 안다는 것을 반영해 **배울 것을 줄이는 방향**으로 4곳을 바꾼다.

### ① 자동화: n8n → **Make** (확정 변경)

| | 변경 전 | 변경 후 |
|---|---|---|
| 도구 | n8n | **Make** |
| 이유 | — | 하는 일이 같은데 **이미 쓸 줄 아는 도구**가 있다. 새 도구를 배울 이유가 없다 |

**Make로 옮기면서 꼭 지킬 것 — 반복은 Make가 아니라 Python에서 돈다.**

Make는 무료 요금제에 **월 실행 횟수(operations) 제한**이 있다(현재 한도는 요금제 페이지에서 확인할 것). 공고 100건을 Make 안에서 반복 처리하면 한 번 실행에 100 operations를 쓴다. 대신 이렇게 짠다.

```
[나쁨]  Make: 공고 목록 받기 → 반복 100회 → 각각 임베딩 → 각각 DB 저장
        = 실행 1번에 수백 operations

[좋음]  Make: 매일 05:00 → POST /batch/collect-contests 호출 1번 → 끝
        Python: 그 안에서 수집·파싱·임베딩·저장을 전부 처리
        = 실행 1번에 2 operations
```

이 방식은 비용만 아끼는 게 아니다. **파싱·임베딩처럼 정확성이 중요한 로직이 코드로 남아 버전 관리가 된다.** Make 화면 안의 로직은 Git에 남지 않는다.

> 기획서 7-2절에서 E가 맡는 "자동화 워크플로우"의 실제 작업은 **"Make 시나리오 4개 + Python 배치 엔드포인트 4개"** 가 된다.

### ② 프론트엔드: TypeScript → **JavaScript** (권장 변경)

| | 변경 전 | 변경 후 |
|---|---|---|
| 언어 | Next.js + TypeScript | **Next.js + JavaScript** |
| 이유 | — | TypeScript는 **배울 축이 하나 더 늘어난다.** 초보자가 타입 에러 하나에 한 시간씩 막히는 일이 흔하다 |

**트레이드오프(솔직하게):** TypeScript는 실수를 미리 잡아 주고, AI도 타입이 있으면 더 정확한 코드를 만든다. 다만 5주라는 기간과 팀 상황에서는 **막히는 시간을 줄이는 쪽**이 낫다고 본다.
팀에 TypeScript를 이미 아는 사람이 있으면 그대로 TypeScript로 가는 게 낫다.

### ③ 인증: 직접 구현 → **Supabase Auth** (권장 변경)

| | 변경 전 | 변경 후 |
|---|---|---|
| 방식 | 직접 구현 (bcrypt 해시, 세션, 재설정 메일) | **Supabase Auth** |
| 이유 | — | 회원가입·로그인·비밀번호 재설정·Google 로그인·비밀번호 해싱이 **설정으로 해결**된다 |

이것 하나로 **E의 작업량이 크게 줄어든다.** `FR-AUTH-01~03`, `FR-JOIN-01`이 "코드 작성"에서 "설정 + 화면 붙이기"가 된다.

**단, 확인이 필요한 것:**

- `NFR-SEC-01`의 "5회 실패 시 60초 잠금"은 Supabase 기본 rate limit으로 충분한지 확인하고, 부족하면 직접 구현한다
- `FR-JOIN-01`의 비밀번호 조합 규칙(영문·숫자·특수문자 각 1자)은 **화면 쪽 검증**을 따로 추가해야 한다
- 명세서의 "bcrypt 해시로 저장"은 "Supabase Auth가 해싱을 처리"로 문구를 수정한다

### ④ Redis: **1차 구현에서는 보류**

파이프라인 다이어그램에는 Redis 카운터가 있고, 그것이 최종 목표 구조로는 맞다.
다만 **실사용자 5~10명 규모에서는 PostgreSQL 테이블로 충분하다.**

| | |
|---|---|
| 1차 구현 | `study_events` 테이블에 기록하고 `SUM()`으로 집계 |
| Redis 도입 시점 | 집계가 느려지는 것이 실제로 관측될 때 |
| 얻는 것 | **배울 기술이 하나 줄어든다** |

발표에서는 "현재 규모에서는 불필요하다고 판단해 도입하지 않았고, 필요 시점의 기준을 정해 두었다"가 **Redis를 억지로 쓴 것보다 나은 설명**이다.

## 2. 전원 공통으로 배워야 할 것

**시간은 "강의를 듣는 시간"이 아니라 "직접 해보며 익히는 시간"** 기준의 대략치다.

| 우선순위 | 항목 | 왜 필요한가 | 어디까지 | 대략 |
|:---:|---|---|---|:---:|
| **1** | **Git · GitHub 협업** | 과제 필수 요건(버전 관리 기록). 못 하면 협업 자체가 불가능 | 브랜치 생성 → 커밋 → PR → 리뷰 → 병합 → **충돌 해결** | 3~4h |
| **2** | **환경변수 (`.env`)** | API 키 관리. `NFR-SEC-02`의 근거 | 로컬 `.env` 읽기, 배포 서비스에 등록하기 | 30m |
| **3** | **REST API 개념** | 프론트와 백엔드가 대화하는 방식 전부 | GET/POST 차이, JSON 주고받기, 상태코드(200/400/401/500) | 2h |
| **4** | **브라우저 개발자도구** | **에러를 스스로 읽을 수 있게 된다.** 이게 없으면 모든 문제를 남에게 물어야 한다 | Console 탭에서 에러 읽기, Network 탭에서 요청·응답 보기 | 1h |
| **5** | **SQL 기초** | 데이터가 제대로 들어갔는지 직접 확인 | `SELECT` `INSERT` `UPDATE` `WHERE` `JOIN` | 3h |

> **4번을 특히 강조한다.** 비전공자 팀에서 진도가 갈리는 지점은 재능이 아니라 **에러 메시지를 읽을 줄 아느냐**다. Console에 빨간 글씨가 떴을 때 그걸 그대로 복사해 AI에게 물을 수 있으면 대부분 풀린다.

## 3. 역할별 추가 학습

### 프론트엔드 — A가 중심이지만 **B·C·D도 자기 화면은 직접 만든다**

수직 분할(기획서 7-1) 원칙상 각자 자기 기능의 화면을 만들기 때문에, **네 명이 이 목록을 봐야 한다.**

| 항목 | 어디까지 | 대략 |
|---|---|:---:|
| HTML · CSS | 레이아웃 잡기, Flexbox, 반응형 기초 | 3h |
| JavaScript | 변수·함수·배열 메서드(`map` `filter`), `async/await`, `fetch` | 5~6h |
| React | **컴포넌트 · props · state(`useState`) · `useEffect`** — 이 4개가 전부다 | 6~8h |
| Next.js | 파일 기반 라우팅(`app/goal/page.js` = `/goal`), 백엔드 호출 | 3~4h |

> **React에서 초보자가 반드시 넘어야 할 벽 하나:** "화면은 state가 바뀔 때만 다시 그려진다."
> 변수를 바꿨는데 화면이 안 바뀌면 십중팔구 `useState`를 안 쓴 것이다. 이것만 이해하면 절반은 넘는다.

### 백엔드 — 전원 (자기 기능의 API는 자기가)

| 항목 | 어디까지 | 대략 |
|---|---|:---:|
| FastAPI | 라우트 만들기(`@app.get`), 요청 받기, JSON 응답, 자동 문서(`/docs`) | 4~5h |
| Pydantic | 모델 정의, 검증 실패 처리 — **AI 응답 스키마 검증의 핵심 도구** | 2h |
| CORS | 프론트(Vercel)와 백엔드(Railway) 도메인이 달라서 **반드시 마주친다** | 30m |

> FastAPI의 `/docs`(자동 생성 API 문서)는 비전공자 팀에 특히 유용하다. **화면 없이도 API를 눌러서 테스트**할 수 있어, 프론트와 백엔드를 따로 검증할 수 있다.

## 5. AI에 맡길 것 vs 직접 이해해야 할 것

기획서 7-3 규칙 1번("설명할 수 없는 코드는 병합하지 않는다")을 실제로 지키려면 이 구분이 필요하다.

| 직접 이해해야 한다 — AI가 대신 못 함 | AI에 맡겨도 된다 |
|---|---|
| **데이터가 어디서 어디로 흐르는가** (화면 → API → DB → 화면) | 문법, 반복되는 코드, 형식 변환 함수 |
| **왜 이 값인가** — 유사도 0.62, 반복 5회, 청킹 600자 | CSS 스타일링, 레이아웃 잡기 |
| **에러 메시지가 무엇을 말하는가** | 라이브러리 사용법, 설정 파일 |
| **우리 기능명세서와 맞는가** | 테스트 코드 초안 |
| **개인정보·API 키가 어디에 있는가** | 더미 데이터, 샘플 |

**AI에게 잘 묻는 법 — 비전공자 팀에 실제로 효과가 큰 것**

1. **에러는 통째로 붙여넣는다.** 요약하지 말고 전문을. 줄 번호와 파일명이 답을 결정한다
2. **맥락을 먼저 준다.** "FastAPI로 만든 API를 Next.js에서 부르는데" 한 줄이 답의 품질을 크게 바꾼다
3. **"왜 이렇게 되는지 설명해줘"를 같이 묻는다.** 코드만 받으면 PR 설명 3줄을 쓸 수 없다
4. **안 되면 "다시 해줘"가 아니라 "어떤 결과가 나왔는지"를 준다.** 무엇이 실제로 일어났는지가 정보다
5. **키·개인정보는 절대 붙여넣지 않는다.** `.env` 내용은 `API_KEY=xxx`로 가려서 묻는다

## 6. 비전공자 팀이 가장 많이 막히는 3곳

미리 알고 있으면 막히는 시간이 줄어든다. **전부 "코드가 틀려서"가 아니라 "설정 때문에" 생기는 문제**라 AI에게 물어도 잘 안 풀린다.

### ① CORS — 프론트와 백엔드 도메인이 달라서

> `Access to fetch at 'https://...' has been blocked by CORS policy`

Vercel(프론트)과 Railway(백엔드)는 도메인이 다르다. 브라우저가 기본적으로 막는다.
**해결:** FastAPI에 `CORSMiddleware`를 추가하고 프론트 도메인을 허용 목록에 넣는다. **1주차에 미리 설정해 두면 나중에 안 만난다.**

### ② 배포 환경변수 — "로컬에선 되는데 배포하면 안 돼요"

1순위 원인이다. `.env`는 Git에 올라가지 않으므로(`.gitignore`), **배포 서비스 대시보드에 같은 값을 따로 등록해야 한다.**
Vercel·Railway·Supabase 각각에 등록한다. 하나라도 빠지면 그 서비스만 조용히 실패한다.

### ③ Google OAuth — 코드가 아니라 콘솔 설정

AI가 코드는 잘 짜 주지만 **Google Cloud Console 설정은 사람이 직접 해야 한다.**

- OAuth 동의 화면 구성, 테스트 사용자 등록(미검증 앱은 여기 등록된 사람만 사용 가능)
- **리디렉션 URI를 로컬·배포 양쪽 다 등록** — 가장 많이 빠뜨리는 부분
- 캘린더 읽기 권한 범위(scope) 지정

기획서 리스크 **R4**에 해당한다. 5~6시간을 잡고 **2주차에 여유 있게** 시작한다.

## 7. 착수 전 실습 과제 (09-11~13)

기획서 7-5절의 "Git 기본 흐름 한 번씩 실습"을 구체화한 것이다. **각자 아래를 한 번씩 한다.**

| # | 과제 | 확인 |
|---|---|---|
| 1 | 저장소를 로컬에 clone한다 | 폴더에 파일이 보인다 |
| 2 | `feat/<이름>-test` 브랜치를 만든다 | `git branch`에 보인다 |
| 3 | `docs/팀원소개.md`에 자기 두 줄을 추가하고 커밋한다 | `git log`에 내 커밋이 보인다 |
| 4 | push하고 PR을 연다 | GitHub에 PR이 보인다 |
| 5 | **다른 사람 PR에 리뷰 코멘트를 하나 단다** | 리뷰가 달린다 |
| 6 | 승인받고 병합한다 | `main`에 반영된다 |

**5명이 같은 파일을 고치므로 충돌이 날 것이다. 그게 목적이다.** 충돌을 안전한 상황에서 한 번 겪어 두면, 2주차에 진짜 코드에서 만났을 때 당황하지 않는다.
