# 탈퇴 프로필 1년 보관 — 1단계 DB 구현

## 정책
- 보관: 이메일, 닉네임, 개인정보/AI/마케팅 동의 여부, 동의 시각.
- 관리 정보: 보관 레코드 번호, 탈퇴 시각, 삭제 예정 시각.
- 제외: 인증 UUID, 비밀번호/해시/토큰, 일정/학습/알림 데이터.
- 탈퇴 시각을 UTC 기준으로 1년 더해 만료 시각을 계산한다. 윤년 2월 29일은 다음 해 2월 28일.
- 매시간 정각에 만료 데이터를 삭제한다. 정상 실행 시 만료 후 최대 약 1시간 지연된다.
- 보관용 private 스키마는 public/anon/authenticated가 접근하지 못하며, service_role에도 테이블 권한을 주지 않는다. DB 관리자만 직접 조회 가능하다.
- 보관의 정책상 목적/사용자 고지는 팀에서 확정해 배포 문서에 반영한다. 이 구현은 법적 적합성 판단을 대신하지 않는다.

## 변경 원리
Auth 관리자 삭제 시 BEFORE DELETE 트리거가 프로필 보관과 서비스 데이터 삭제를 수행한다.
보관/삭제에 오류가 나면 Auth 삭제까지 동일 트랜잭션에서 롤백된다.
따라서 Supabase 대시보드 등에서 관리자가 직접 계정을 삭제할 때도 이 보관 정책이 적용된다.
users를 먼저 삭제하지 않는다. 프로필이 없는 Auth 계정은 보관본 없이 연결 데이터만 정리한다.

현재 운영 DB에서 확인한 auth_id UUID + study_plans.user_id bigint 스키마용이다.
004의 UUID user_id로 통일된 다른 DB에 그대로 적용하면 사전 검사에서 중단된다.
처리 대상 테이블 목록은 SQL에 명시한다. 새 사용자 데이터 테이블을 추가하면 삭제 목록/관계도 검토해야 한다.
익명 세션으로 저장된 데이터는 Auth ID로 연결할 수 없으므로 이 기능의 삭제 범위 밖이다.

## 검증 실행 (운영 DB 불필요)
PowerShell, 저장소 루트:

    Push-Location tools/retention-db-test
    npm ci
    node check.mjs
    Pop-Location

PGlite PostgreSQL 엔진에서 다음을 확인한다:
- 보관 실패 시 Auth/프로필/일정 삭제 롤백
- 본인 데이터만 삭제, 다른 회원 데이터 유지
- 연결 알림과 block_id가 없는 본인 알림까지 삭제
- 보관 필드 제한, 역할별 접근 제한
- 1년 만료 계산, 윤년, 만료 전 보존 및 만료 후 삭제
- 트리거 또는 예약 작업이 꺼지면 준비 상태 false

cron 스키마/등록 함수는 테스트 대역이다. 실제 pg_cron 시간 실행과 Supabase Auth API 호출은 이 테스트에 포함되지 않는다.

## 운영 적용 — 아직 실행하지 않은 단계
1. 이 DB 단계 변경을 커밋하고 작업 브랜치에 push한다.
2. API/UI 단계의 수정과 테스트를 완료한다. 현재 배포된 탈퇴 API는 잘못된 user_id를 조회하며 1년 보관 준비 확인을 하지 않는다.
3. 별도 Supabase 테스트 프로젝트에서 같은 스키마로 마이그레이션을 검증한다.
4. pg_cron 확장을 활성화한다. SQL은 cron.schedule이 없으면 전체 롤백된다.
5. SQL Editor에서 010_withdrawal_retention.sql을 한 번 적용한다. 기존 기록 덮어쓰기를 막기 위해 재실행 시 기존 테이블/함수 오류로 중단하도록 설계했다.
6. 서비스 키만 허용된 public.withdrawal_retention_ready() 결과 true와 cron.job의 active 값을 확인한다.
7. API/UI를 배포하고 전용 테스트 계정으로 탈퇴/재로그인 실패/보관 필드/타인 보존을 확인한다.
8. cron.job_run_details에서 예약 실행 성공을 확인하고 실패를 운영 모니터링 대상으로 둔다.

이 단계는 SQL과 테스트 파일 제공 및 로컬 검증까지만 완료했다. 운영 DB 적용, 실제 계정 삭제, 자동 만료 작업 실행을 완료한 것으로 기록하지 않는다.
