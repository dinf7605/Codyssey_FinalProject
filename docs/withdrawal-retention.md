# 탈퇴 프로필 1년 보관 — 1단계 DB 구현

## 정책
- 보관: 이메일, 닉네임, 개인정보/AI/마케팅 동의 여부, 동의 시각.
- 관리 정보: 보관 레코드 번호, 탈퇴 시각, 삭제 예정 시각.
- 제외: 인증 UUID, 비밀번호/해시/토큰, 일정/학습/알림 데이터.
- 탈퇴 시각을 UTC 기준으로 1년 더해 만료 시각을 계산한다. 윤년 2월 29일은 다음 해 2월 28일.
- 매시간 정각에 만료 데이터를 삭제한다. 정상 실행 시 만료 후 최대 약 1시간 지연된다.
- 보관용 private 스키마는 public/anon/authenticated가 접근하지 못하며, service_role에도 테이블 권한을 주지 않는다. DB 관리자만 직접 조회 가능하다.
- 보관의 정책상 목적/사용자 고지는 팀에서 확정해 배포 문서에 반영한다. 이 구현은 법적 적합성 판단을 대신하지 않는다.

## 변경 원리
Auth 관리자 삭제 시 BEFORE DELETE 트리거가 프로필을 보관하고, 서비스 데이터는 외래키가 지운다.
보관에 오류가 나면 Auth 삭제까지 동일 트랜잭션에서 롤백된다.
따라서 Supabase 대시보드 등에서 관리자가 직접 계정을 삭제할 때도 이 보관 정책이 적용된다.
users를 먼저 삭제하지 않는다. 프로필이 없는 Auth 계정은 보관본 없이 연결 데이터만 정리된다.

**공용 DB(studypace) 스키마 기준 (2026-09-27 다시 씀).** 사용자 테이블은 모두 `user_id uuid → auth.users on delete cascade`
(backend/README.md "DB 기준")라서 트리거가 테이블을 하나씩 지울 필요가 없다. `ai_call_logs` 만 `on delete set null` 이라 트리거가 따로 지운다.
**새 사용자 데이터 테이블은 반드시 `user_id … on delete cascade` 로 만든다** — 그러면 탈퇴 삭제 목록을 따로 고칠 일이 없다.

처음 판(auth_id·bigint user_id 스키마)은 공용 DB 가 아닌 다른 Supabase 프로젝트용이었다. 아래 "적용 및 실제 연동 검증" 기록은 그 DB 에서 한 것이다.
공용 DB 에는 2026-09-27 새 판을 적용했고 `withdrawal_retention_ready() = true` 를 확인했다 (pg_cron 활성화 포함).
PGlite 검사(`tools/retention-db-test`)도 새 스키마로 바꿔 통과했다. 공용 DB 에서 실제 계정으로 탈퇴해 보는 확인은 아직 하지 않았다.
익명 세션으로 저장된 데이터는 Auth ID로 연결할 수 없으므로 이 기능의 삭제 범위 밖이다.

## 검증 실행 (운영 DB 불필요)
PowerShell, 저장소 루트:

    Push-Location tools/retention-db-test
    npm ci
    node check.mjs
    Pop-Location

PGlite PostgreSQL 엔진에서 다음을 확인한다:
- 보관 실패 시 Auth/프로필/일정 삭제 롤백
- 본인 데이터만 삭제, 다른 회원 데이터 유지
- 연결 알림과 block_id가 없는 본인 알림까지 삭제
- 보관 필드 제한, 역할별 접근 제한
- 1년 만료 계산, 윤년, 만료 전 보존 및 만료 후 삭제
- 트리거 또는 예약 작업이 꺼지면 준비 상태 false

cron 스키마/등록 함수는 테스트 대역이다. 실제 pg_cron 시간 실행과 Supabase Auth API 호출은 이 테스트에 포함되지 않는다.

## 적용 및 실제 연동 검증 (2026-09-27 KST)

### 확인 완료
- Supabase에 010_withdrawal_retention.sql 적용 및 pg_cron 활성화.
- 백엔드 서비스 키 설정 수정 후 withdrawal_retention_ready() = true 확인.
- 실제 Supabase를 사용하는 FastAPI TestClient로 신규 가입, 로그인, 본인 인증, 프로필 조회 통과.
- 탈퇴 미동의 요청 차단 및 계정 유지 확인.
- 탈퇴 성공, 활성 프로필 삭제, 재로그인 및 기존 액세스 토큰 차단 확인.
- 테스트 프로필의 별도 보관과 정확히 1년 뒤 만료일 설정 확인.
- purge-withdrawn-profiles 작업의 최근 5회 매시간 실행 succeeded 확인.
- 브라우저에서 계정 프로필 및 1년 보관 안내, 탈퇴 확인창 표시 확인.
- 브라우저 탈퇴 후 해당 이메일의 Auth 계정과 활성 프로필은 없고 보관 프로필은 존재함을 SQL로 확인.
- 브라우저에서 탈퇴 계정의 재로그인 실패 확인.

### 화면 보완
- 탈퇴 API 성공 후 로그인 정보를 지우고 탈퇴 완료 및 1년 보관 안내를 표시한다.
- 안내 확인 후 router.replace('/')로 첫 화면으로 이동한다.
- 2026-09-27 KST: 실제 브라우저에서 탈퇴 완료 및 프로필 1년 보관 안내창 표시를 확인했고, 확인 버튼을 누른 뒤 첫 화면(로그인 화면)으로 이동함을 확인했다.

### 검증 범위와 운영 유의사항
- 예약 실행의 "1 row"는 함수 조회 결과 행 수이며 삭제된 프로필 수가 아니다.
- 실제 DB에서 1년이 경과한 프로필의 삭제는 아직 관찰하지 않았다.
- 만료 전 보존, 만료 후 삭제, 윤년 계산 및 실패 시 롤백은 별도 PGlite 테스트 범위다.
- 이번 실제 신규 계정 테스트는 학습 데이터를 생성하지 않았으므로, 데이터가 있는 계정의 연관 데이터 전체 삭제까지 검증한 것은 아니다.
- 브라우저에서 탈퇴 확인창 취소 후 계정 유지 여부는 별도 확인이 필요하다.
- 로컬 브라우저와 연결된 Supabase 검증이며 배포 서버의 환경변수 및 배포 상태를 보증하지 않는다.
- 프로젝트 최상위 .env의 SUPABASE_SERVICE_ROLE_KEY에 관리자용 키를 설정한다.
- .env와 실제 키, 비밀번호, 토큰은 커밋하거나 검증 문서에 기록하지 않는다.
- 예약 작업 실패 여부를 지속적으로 모니터링한다.
